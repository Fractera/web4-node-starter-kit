# 663-4 — waking: the calendar 2 minutes ahead, the gatekeeper on a call (plan)

**Built.** (a) The calendar: the core's minute clock (`lib/main-agent-cron/runner.ts`) also reads the `data/cron.json` of every sleeping
element that has one (the same «is it due» rule as `lib/cron/due.ts`); 2 minutes before a due entry it turns the element on
(`element-power on`, `powerAuto`), and after the entry ran (its run journal) plus a grace of 5 minutes puts it back to sleep if the rule
still wants it asleep. (b) The gatekeeper — one resident process `fractera-gatekeeper` (`scripts/gatekeeper.mjs`, ~50 MB, named to the
owner — «Привратник (Рекомендую)»): it listens on the ports of sleeping `wakeOnCall` elements (the registry, re-read on each change); the
first request starts the element, the request waits for its `/api/health` (cold start measured), then the port is handed back and the
request is passed through; a `never` element is never behind it. The installer (`ecosystem.config.cjs`) builds it; it holds no port of a
running element.
**Done:** a sleeping element still does its calendar work and still answers its neighbours, A2A and visitors — late by its cold start.
**Proven:** lab — a sleeping lab element with an entry at now+3 min → on at now+1, the entry ran, asleep again; a call to a sleeping
element through the gatekeeper → 200 after N s; negative controls: a call with the gatekeeper stopped → connection refused; an element
`never` → the gatekeeper does not listen on its port.
**Not in it:** keeping elements warm on a schedule of visits.
