## Why a new block
The catalogue (v1.4.18) has no scheme of containment: `block-flow` is steps in order, `orbit-layers` layers in motion, `group` a bare
container. The law: «An interface is needed — first a ready block; none — a new section in Blocks, then its reuse».

## What is built
- `registry/src/sections/blocks/access-map.server.tsx` — kind `block-access-map`: an outer frame (who sees everything: title, one line)
  and inside it 2–6 tiles (each: title, one line «только своё»), a mark between neighbouring tiles that they do not see each other.
  Server-rendered, no script, colours and type from Design (`--type-scale`, tokens), every container with `data-block`, works at 390 px
  (tiles in a column) and in dark theme.
- Its card (`.card.json`), a sample with the memory's words in the showcase (`#showcase`), `SECTIONS.json` and `taxonomy.json` entries,
  the README of the block. Generic words: the same block draws roles or any «one sees all, each sees its own».

## Done when
The block is in the catalogue with its sample, and an element takes it by `npm run blocks -- add block-access-map`.

## How it is proven (named in advance)
1. **Eyes** on the Blocks site's showcase: 1440 and 390 px, light and dark — frame and tiles «виден», no overlap, no console errors.
2. **Guards** of the Blocks element's prebuild (block ids, contrast, typography); **negative control:** the sample with a tile missing its
   line → the block's own data check refuses it.
