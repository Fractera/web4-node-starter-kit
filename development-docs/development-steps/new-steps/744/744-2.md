# 744-2 — no foreign page acts through the node

**Done when:** a state-changing request that a browser sends from another site (`Sec-Fetch-Site: cross-site`, or an `Origin` that is not
the node's own) is refused with 403 before any door runs — on every door of the core; same-origin pages, services and scripts pass.

## Measured before (`probes/csrf.sh`)
`cross → 200` and the server's state read over SSH as root; the same request reaches `/api/node/update`; 74 POST doors; no check in `proxy.ts`.

## What is built (D48)
- `proxy/common.ts` (744-1): for `POST|PUT|PATCH|DELETE` on `/api/*` and the architect's `…/api/…` doors — refuse when
  `Sec-Fetch-Site` is `cross-site` or `same-site`, or when `Origin` is present and differs from the request's own scheme+host; answer
  `{ ok: false, reason: "cross-site" }` 403. Requests without browser headers (services, curl, Telegram, element doors with keys) pass.
- The launch door additionally requires `content-type: application/json` (a cross-origin JSON POST needs a preflight the node never grants).

## How it is proven
1. **Request plane, with a negative control:** `probes/csrf.sh` after the update → `cross → 403` (no SSH happened: the server's `auth.log`
   shows no login at that second), `same → 200`; a scan test `scripts/cross-site-wall.test.mjs` sends the cross-site headers to every POST
   door path listed by `git ls-files 'app/api/**/route.ts'` against the proxy function → all 403; a request with no browser headers → passes.
2. **Live plane:** the launch page works as before in the owner's Chrome (its requests are same-origin): connect, state, install.

## Not in it
A login form or tokens for localhost (the owner at the keyboard stays without sign-in).
