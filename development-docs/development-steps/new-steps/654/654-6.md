# 654-6 — the custom template and root on their own key only (core installer, custom template, root)

**Repositories:** `Fractera/web4-node-starter-kit` (`scripts/services-install.mjs`, `lib/element-key.cjs`, `scripts/node-type.mjs`, pins);
`Fractera/fractera-custom-item-starter` `main` → next after v0.3.157 (skill `release-template`); `Fractera/fractera-root-starter` → next
after v3.0.22 by `npm run template -- rollout custom …`.

## What is built

- **The installer:** a new kind `# kind: element-key` → `ELEMENT_KEY=<id>.<mac>` computed from the node's `DATA_SECRET` by
  `lib/element-key.cjs` (the same test vector as the stores). The carry-over of undeclared variables (265-6) never keeps `DATA_SECRET` in
  an element whose `.env.example` does not declare it — named in the code as the node's master key. Natives are untouched: they declare
  `DATA_SECRET` and keep the node's view.
- **`npm run node-type -- get`** names every custom element that still holds the node's data key (born from a template before this
  release) — in an app factory the architect sees which elements are not separated yet; nothing is stripped by force (654-main §3).
- **The template** `.env.example`: `DATA_SECRET` leaves the `# kind: secret` group (`SETTINGS_SECRET` stays — step 655); `ELEMENT_KEY=`
  under `# kind: element-key`; `GRAPH_URL=` under the neighbours (`# kind: derived`).
- **Every store helper of the template on the element key** (`X-Element-Key`; `X-Data-Secret` only when `ELEMENT_KEY` is absent — a
  developer's laptop with an old downloaded environment): `lib/fractera/data-service.ts`, `lib/db/remote-client.ts`, `lib/db/index.ts`
  (its `SCHEMA` and `DROP_LEGACY` now run in the element's own database), `lib/media/by-name.ts` (its own files and the node's public
  ones; its own name wins), `app/api/media/upload/route.ts` (`visibility`, default public), `app/api/media/[id]/file/route.ts` and
  `app/api/media/icons/...` (public files only; a visitor's cookie is never passed to a store), `app/api/media-proxy/[...path]/route.ts`
  (the element's own files for its people, `?private=1`; today it sends no key and answers 502), `scripts/seed-media.mjs`,
  `scripts/seed-media-when-ready.mjs`, `lib/fractera/vectors.ts`, and `lib/fractera/knowledge.ts` rewritten to the graph element's doors
  (`GRAPH_URL` + `/api/graph-insert`, `/api/graph-query`, `/api/graph-status`; the dead `/service/rag/*` path removed).
- `npm run stores` (`scripts/stores.mjs`) in the template: one line per store — what this element's key opens there (`element <id>`) and
  how much of its own it holds; `--probe` writes one marker into each store and removes it (`--keep` leaves it for a check from another
  element, `--clean` removes it). The element's agent knows its stores before it
  speaks about them (CLAUDE.md §4 «Know yourself»).
- The template's skill `use-own-stores` (and a README section «Your stores»): the element's own database, files (public or private),
  vectors and graph space, what it never sees, how the main agent sees it.
- Release, pin, rollout to root (the files above), root rebuilt by `node:update`.
- **The second custom element (the owner's choice in the window):** a temporary element born from the new template on the owner's node
  (`npm run create`), removed after the proof by «Удалить насовсем» (`DELETE /api/architect/items/<id>`, its address typed back) with
  his yes.

## Done when

Root works on its own key alone — its pages show their images, its stores answer «element root» — and a second custom element sees
nothing of root's.

## How it is proven (named in advance)

1. **On the owner's node:** the variable NAMES of root's `.env.local` include `ELEMENT_KEY` and exclude `DATA_SECRET` (a script prints
   names only); `npm run stores -- --probe` in root → «element root» in data, storage, vectors and graph; root's home page by `npm run
   eyes` — its images there, 0 console errors; `/api/media/<seed id>/file` through the temporary address → 200; `npm run node-type -- get`
   lists no custom element with the node's data key.
2. **Across elements:** the second element's `npm run stores -- --probe` → «element <its id>»; root's marker (left by `npm run stores -- --probe
   --keep`) is not listed by the second element in any store (**negative control**); the master key sees both
   markers, each under its element; then both markers removed and the temporary element removed (his yes). Lab: the template's whole
   prebuild 0, `tsc` 0, `next build` 0 in the workshop; the installer's new kind on a scratch `.env.example` (unit check of the line and of
   the carry-over exception); CI three-os green on the core, the template and root.

## Rests on

654-1 … 654-5 (the stores take the element key); the template release path (`release-template`); `node:update`.

## Not in it

`SETTINGS_SECRET` out of custom elements (655); natives on their own key (they keep the node's view by design); custom elements of other
nodes born from older templates — separated when their owner takes the update (named by `node-type get`); wiping an element's spaces in
the stores when the element is deleted (`lib/web4-items/element-delete.ts` removes the folder, the stores keep its data) — proposed next.
