# 654-1 — the element's own key and its own database (data element; the lock into storage and vectors)

**Repositories:** `Fractera/fractera-data-starter` `main` → next patch after v2.2.4; `fractera-storage-starter` and
`fractera-vectors-starter` get the same `lib/data-store/auth.mjs` (no behaviour of theirs changes until 654-2 / 654-3); the core pins.

## What is built

- **The key** — in `lib/data-store/auth.mjs` (the one lock of data, storage and vectors): `elementKeyOf(id)` = `<id>.` +
  base64url(HMAC-SHA256(`DATA_SECRET`, `fractera-element-key:v1:<id>`)) and `requireAuth`'s third way in — the header `X-Element-Key`:
  the id is split at the first dot, the mac recomputed and compared in constant time → `req.element = <id>`, `req.authVia = 'element'`.
  The master key and the session cookie work as before (`req.element` empty = the node). A test vector (a fixed secret and id → a fixed
  key) is checked by the element's prebuild, so a copy that drifts in any store is caught.
- `requireCapability`: an element key passes the data class; the schema class (`/db/migrate`, `DELETE /db/tables/:t`) passes too, but
  only on the element's own file (below).
- **The element's own database** — `db.mjs`: a call with an element key works on `data/elements/<id>.db` (beside `APP_DB_PATH`, opened
  once per process and kept, WAL, `foreign_keys = ON`), created at its first call; every `/db/*` door (tables, rows, insert, patch, drop,
  migrate) does exactly what it does today, on that file. The master key works on the node's file as today; with `?space=<id>` it works
  on that element's file (the main agent sees all). SQL of an element call that names `ATTACH`, `DETACH`, `VACUUM INTO` or
  `load_extension` is refused (400 `outside-own-database`) — the only ways out of one SQLite file.
- `POST /db/claim` `{ element, tables: [...] }` — master key only: COPIES the named tables of the node's file (schema and rows) into the
  element's file; refuses a table that already exists there. The architect's tool for a node whose custom element wrote tables into the
  shared file before 654 (654-main D5); nothing calls it by itself.
- The forward of the former addresses `/media/*` and `/vectors/*` (`express-shim.mjs` `forwardTo`) already passes every header as it is,
  so `X-Element-Key` reaches storage and vectors unchanged — checked by the proof, not assumed.
- `GET /whoami` — `{ scope: 'node' }` or `{ scope: 'element', id }`: the caller learns what its key opens (one line in `/capabilities`
  too: `auth.element: 'X-Element-Key: <id>.<mac>'`).
- README of data: section «Whose tables» (the element's own file, the node's file, `?space=`, `claim`, the refusals).

## Done when

A table made with A's key is seen by A and by the master key with `?space=A`, and not by B.

## How it is proven (named in advance)

1. **Doors on the owner's node** (data delivered by `node:update`; keys computed by the proof script from the node's `DATA_SECRET`, never
   printed): with A = `root`: `CREATE TABLE t654 (v TEXT)` + insert «a654» → 200; `GET /db/tables` with A → `t654`; **with B =
   `blocks` → no `t654` (negative control)**; B makes its own `t654` with «b654» — A still reads only «a654»; the master key → no
   `t654` in the node's file, `?space=root` → «a654»; B's `ATTACH DATABASE '…data.db' AS x` → 400; a key `blocks.<root's mac>` → 401;
   `/whoami` with each key names its scope. The proof removes what it made: `t654` dropped in both files, `blocks.db` deleted.
2. **The files directly:** `data/elements/root.db` and `data/elements/blocks.db` exist beside the node's `data.db`; the node's file
   holds its 7 tables and no `t654` (read with the master key, table list only). Lab before delivery: unit checks of the key (derive,
   verify, a swapped id, a cut mac, an empty secret → refused), the SQL refusals on SQLite, prebuild 0, `tsc` 0, `next build` 0 in the
   clone; CI three-os green on all three repositories.

## Rests on

`auth.mjs` as the one lock of three elements (550); `APP_DB_PATH` resolved from the element folder (`context.mjs` — never `cwd`, 260-1).

## Not in it

Storage and vectors behaviour (654-2, 654-3); the installer writing `ELEMENT_KEY` and the template using it (654-6); a page that browses
an element's tables (the main agent reads them with `?space=`); moving tables automatically (D5).
