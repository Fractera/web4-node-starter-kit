# 670-8 — No call is lost during an element's cold start (DECISION FIRST)

Created 2026-11-07 from 670-1 (route A — the same capability, waking on an order): a second call during blocks' 2.9 s cold start got
`ECONNREFUSED` at once. The gatekeeper releases the port so that the element can take it; until the element listens, the port is
nobody's. The owner's goal: «Когда … постучится заказ, нужно немедленно пробудить агента».

## Two ways — the owner chooses before any code
1. **The caller waits (recommended).** The node's i2i client retries a refused connection with a short backoff, up to the cold-start
   limit (the gatekeeper's own 120 s; measured 2.9 s), only when the registry says the callee sleeps by the rule — no resident cost, no
   change to the gatekeeper; the core's callers here, the elements' client in 671. An a2a caller from outside never sees the window: its
   order is answered with an A2A Task at once (670-6's plan).
2. **The gatekeeper never lets go.** Elements that may sleep listen on an inner port and the gatekeeper stays a permanent proxy in front
   of them — no window at all, but every call of those elements passes one more hop forever, and the gatekeeper becomes a single point of
   failure for them (the instruction: «there is no single point of failure»).

## What counts as done (way 1)
Two calls 1 s apart to an asleep element both answer 200; a call to a person-turned-off element still fails fast (no retry loop).

## How it is proven (way 1)
1. The 670-1 script with the retrying client: call 1 and call 2 → 200 and 200. 2. Negative control: stripe (off by the person) →
   refused in under 1 s, no retries (the registry says «off by a person», not «asleep»).

## Not in it
Any change to the gatekeeper (way 2 only on the owner's word); the elements' client (671).
