# 741-4 — a server never opens a quick tunnel

**Done when:** on a server node no command and no button can start `fractera-web4-tunnel`, and `logs/tunnel.json` `unpublished` again
means only «the person took the site off the internet» (371-1).

## What is built
- `scripts/serve.mjs`: `start` skips the tunnel when `nodePlace(root).kind === "server"` (today: only the `unpublished` flag);
  `publish` (and `publish --new`) on a server refuses with one line — «у узла на сервере лицо — nginx и его домен; временный адрес
  здесь не открывается» — and exit code 2, writing nothing. The check comes BEFORE any write to `logs/tunnel.json` (today `publish`
  rewrites the file and drops the server's `unpublished` mark).
- `app/api/domain/new-address/route.ts` (the dead-address alarm's door): on a server → 409 `{ reason: "server-node" }`; the alarm itself
  is hidden there by 741-6.
- `scripts/dedicated-server/install.sh` keeps writing its mark (old servers read it until their first start with 741); its comment
  says the place record is the reason now.

## Proof — two planes, named in advance
1. **Unit:** the decision helper (extracted pure function `tunnelAllowed({ kind, unpublished })`) — server → never; home + unpublished →
   no (371-1 kept); home → yes. **Negative control:** home rows equal today's behaviour.
2. **Live:** on the test server (the agent's SSH): `npm run serve:publish` → the refusal line, exit 2, `logs/tunnel.json` unchanged
   (`sha256sum` before and after), `pm2 jlist` without `fractera-web4-tunnel`. On this computer: NO publish run (it would rotate the
   address — CLAUDE.md §2); `npm run serve:status` shows the same quick-tunnel address as before the update — the negative control
   that the computer still publishes.
