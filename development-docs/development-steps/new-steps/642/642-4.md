# 642-4 — A failure says what happens next

**What is built.** At the end of a failed build the terminal shows a closing block, not just red lines:
1. what fell, in plain words, from the known causes (memory: «memory allocation … failed»; a type error; a guard of `prebuild` by
   its name; the network of npm), and the step;
2. «Прежняя версия возвращена и работает» (for an element: its previous build is on; for the core: the backup `.next`), proven by the
   process answering, not assumed;
3. the next state, shown before it starts:
   - a passing cause (memory, the npm network) → one automatic retry, named with its reason: «Повторяю один раз: не хватило памяти,
     освобождаю и собираю снова (попытка 2 из 2)»; a second failure — no more retries;
   - a cause in an element's code → a button «Передать агенту элемента»: the element's own agent gets the log and the task, fixes,
     commits, the board redeploys after its word; the terminal shows «агент <id> разбирает ошибку…» (the core does not read the code);
   - a cause in the core's own code → «Сообщить Fractera»: the log and the version for the upstream; the node keeps the previous build.

**Done when.** A deliberately broken element build on a test element shows the block with the right cause and a working previous
version; a simulated memory failure shows one visible retry and then the end.

**How it is proven.** 1. The cause recognizer over saved real failure logs (553-6 memory, a type error, a guard): each named right.
Negative control: a successful log names no cause. 2. Live on a test element (not the owner's sites): a broken build → the block, the
previous version answering 200; «Передать агенту» starts its agent with the log (the task file in its intake).

**Rests on.** 642-1, 642-2. **Not in it.** Retries of anything but the two passing causes; the agent fixing the core.
