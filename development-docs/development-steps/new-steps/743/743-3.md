# 743-3 — one door for transitions: the migration ledger

**Done when:** every one-time transition between versions is a numbered file run by one runner that every entry point calls, recorded
in `data/node/migrations.json`, and the place migration of 741-2 no longer hangs on `start` and `rebuild` by hand.

## What is built
- `lib/migrations/` — one file per migration, `<step>-<slug>.mjs`, exporting `id` (= file name), `why` (one line), `run(root) →
  { done: true, note } | { done: false, reason }`, idempotent by contract (a second run changes nothing). `README.md` of the folder:
  the contract, how to add one, the rule «never call a migration directly». First file: `741-2-place-record.mjs` wrapping
  `migratePlaceRecord` (`lib/hosting/place.mjs`).
- `scripts/migrate.mjs` — the runner: reads the folder in name order, skips ids in the ledger, runs the rest, appends `{ id, at, result,
  version }` to `data/node/migrations.json` (written atomically: tmp + rename), prints one line per migration, exits 0 even when one
  fails (the failure is recorded and named; a migration never stops a start). `npm run migrate` in `package.json`.
- Every entry point that brings code to life calls the runner once: `scripts/serve.mjs` `start` (replaces l. 152-157) and `rebuild`
  (replaces l. 683-685, 8f165354); the computer's installation (`scripts/launch.mjs`, after `fresh-project`); the server's installation
  (`scripts/dedicated-server/install.sh`, a stage `migrate`); the target's updater (743-2) after the merge, before the guards.
- Guard `scripts/check-migrations.mjs` in `prebuild`: (a) a function exported by a migration file is imported only by the runner; (b)
  every file in `lib/migrations/` has the contract (`id`, `why`, `run`); (c) the runner is called from the four entry points named above
  (a removed call is refused).

## How it is proven
1. **Runner plane, with a negative control:** a scratch node: first `npm run migrate` → the ledger has `741-2-place-record` with a
   result; the second run → the ledger byte-equal, «nothing to do»; a planted direct `migratePlaceRecord(root)` in a scratch copy of
   `scripts/serve.mjs` → `check:migrations` refuses it; a removed runner call from `rebuild` → refused.
2. **Live plane:** this computer after its node update: `data/node/migrations.json` exists and lists `741-2-place-record`, written at the
   update's time by `rebuild` with nobody's hand (this morning's miss inverted; the record was already v2 → result «kept»). The test
   server after 743-5: the same id with result «written» (its place record was never migrated).

## Rests on / not in it
Rests on 741-2 (`migratePlaceRecord`). Not in it: database schema migrations of elements (each element's own), down-migrations (a
rollback is a new version, `CLAUDE.md` §4).
