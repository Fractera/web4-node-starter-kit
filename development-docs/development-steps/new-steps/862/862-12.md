## Substeps
1. **One shared list in the core** — the shared drawer entries live in one place of the core; the core's drawer reads it. The marketplace
   entries are found by `provides: market-client` (never by id), with the client's own address; no client → no entries.
2. **A core door for the elements** — `GET /api/node/account-links?lang=` with the element's own key → the shared entries with absolute
   addresses. The core never pushes; the element pulls (CLAUDE.md §6: code speaks only through agreed APIs).
3. **The templates** (custom and native): the drawer asks that door when it is opened (a click, so the static pages stay static) and shows
   the shared entries under its own; a change of the list needs no element rebuild. An element skips entries pointing at its own address
   (market keeps its own three once). Release custom and native with Roma's key (window), pin, roll out to the born elements.
4. **Access for an element's own person** — the client's three pages open to the architect and to the admin of any element of this project
   (the person of that element, like Marina); a guest gets the lock; paying stays the payer's own act in a window. market's agent builds it
   (task), the core answers its questions.
5. **Proofs.** Mac: the drawer of the core, of root and of a custom element (fc4vk) shows the three entries; a click opens the client's
   page; an element admin's test account sees the pages, a guest gets 401/lock (negative). Server behind the wall (aifa.dev, the test
   buyer): after the update, the same from a walled element's drawer, and a free starter taken end to end.
