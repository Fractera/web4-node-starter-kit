# 670-4 — `find` says why: «does it now / nearest by its area / matches only its description»

**Repository:** Fractera/web4-node-starter-kit — the commit of this summary (`git log -- development-docs/development-steps/completed-steps/670-4.md`).

## What was done and how
- `lib/a2a/self-description.cjs`: `indexPieceList` — every piece carries its kind (`name`, `description`, `role`, `skill` + its id,
  `area`); the element's area and the jobs it may grow into are ONE piece («<area> It may grow into: a; b; c.»), the way a skill is its
  description with its examples. `findByMeaning` returns for every hit its best piece `{ kind, ref, text, score }`; index layout 2 — the
  whole descriptions in their own collection `node-elements-whole`, so more pieces never push a whole out of the 100 vectors a search
  returns (a ledger of the old layout is dropped vector by vector and indexed again — the live node migrates by itself at its next
  `find`); the ledger's hash covers the pieces too (an area change re-indexes). Options `collection`, `wholeCollection`, `ledgerFile`,
  `prefix`, `embed` — for measuring in isolation; production calls pass none. `whyOf(hit)` — the reason in words.
- `scripts/main-agent-cli.mjs`: every `find` candidate line says its reason; the duplicate stop of `create` says it too and, for an
  area match, «a route its own agent builds there, not a new element». `FIND_MIN` stays 0.25 — with the measurement in its comment.

## The plan's criterion — NOT met as written, and why
The plan said «both of the owner's examples answer "nobody" and storage is no longer a candidate». Measured: right elements matched by
their description score 0.30–0.57 and jobs the node lacks 0.29–0.38 — no threshold separates them; a cut at 0.40 for description-only
matches would lose three real hits (a photo link → storage 0.37, a pricing section → blocks 0.30, «войти на сайт по паролю» → auth
0.38), and a miss is what births a duplicate element (603-2). So storage stays a candidate for YouTube at 0.38 — but the line now says
it matches only its description (ffmpeg trimming), not a skill and not its area. The decision moves where it can be made: the main
agent reads the card, by the law of 670-5; 670-7 checks live that it does not route the YouTube summary to storage.

## Mistakes
- **Nearly a live-index corruption.** The first measurement script indexed into «isolated» collections with the production ids
  (`self-<id>-<i>`); if the vectors element keeps ids store-wide, the run would have overwritten the live node's vectors and the cleanup
  deleted them. Caught before the run; fixed with the `prefix` option (`m670a`, `m670n`, `m670b…`) and the live ledger hash checked
  before and after. Rule for myself: an «isolated» run isolates the NAMES, not only the collection.
- The first idea — each job it may grow into as its own piece — made false «area» matches stronger (0.52); measured, not shipped.
- The plan's rule «weak by kind + score» was dropped after the measurement: no score rule exists for description matches.

## Evolution of skills
- `route-to-element` / `shape-the-need` must read the three reasons (670-5): «does it now» → wake its worker; «nearest by its area» →
  a route there after the card confirms; «matches only its description» → a hypothesis, usually nobody.
- ANTI-PATTERNS candidate (All systems): «A measurement against a live store isolates the ids, not only the collection» — proposed to
  the owner with 670-5's lines.
