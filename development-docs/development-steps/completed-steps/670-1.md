## What was done and how
A live check of 663-4 with the node's own commands, no change to anything: blocks (`switch: auto`, `wakeOnCall: true`) was put to sleep

## What came out
- The process layer of an i2i order works on the owner's node: the port is taken over 0.6 s after the sleep, the first call is held and
  answered 200 after a 2.9 s cold start, the element is on afterwards; an element turned off by a person stays off and is refused.
- **A measured limit, not new but now with numbers:** a second call during those 2.9 s is refused at once (`ECONNREFUSED`) — the port is
  nobody's while the element rises (named in the gatekeeper's header and in `element-power`). Against the owner's «нужно немедленно
  пробудить» a second concurrent caller loses its call → substep 670-8 (a decision first).

## Mistakes
- I looked for the gatekeeper's journal in `~/.pm2/logs`; the node writes its own `logs/gatekeeper.log` — one wasted call.
- I read element ports from `logs/runtime.json` because the instruction says «a port is asked from `logs/runtime.json`»: that file holds
  only the core's port; element ports are in the registry and in `serve:status`. The instruction's line is imprecise → proposed in
  670-5's window (sections 1–8 change only by the owner's word).
- On the node, Bash reads of the core's own `lib/web4-items/*` were refused «by a deny rule» while the only rule is
  `Read(./WEB4-ITEMS/**)`; the Read tool with the workshop's absolute path works. Cause not established (a case-insensitive match on
  macOS is my guess, unchecked) — noted, not chased.
