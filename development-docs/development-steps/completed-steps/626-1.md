## The decision
**Node.js in the element's own process: `@huggingface/transformers` 3.8.1 with `onnxruntime-node` 1.21.0; the model file
`model_optimized.onnx` of `Qdrant/paraphrase-multilingual-MiniLM-L12-v2-onnx-Q` (235,052,644 bytes, sha256
`634d0f66c29dc934c8fa72b8a4fe91dd4d420a22f1d82a241058d4316e659a99`) with its `tokenizer.json` (sha256
`fa685fc160bbdbab64058d4fc91b60e62d207e8dc60b9af5c002c5ab946ded00`); 128 input tokens, mean pooling, normalized.** Why: the model runs
inside the element's server (no Python and no second resident process for this element; it installs with npm like every element);
its vectors equal Python's to the sixth digit; the speed is the same; the 235 MB file keeps ~300 MB less resident than the 470 MB fp32
export at cos ≥ 0.999997 between the two. Apache-2.0 (the model and both exports) — the element's release may carry the file.

package's `bin/napi-v*/darwin/`); 1.20.1 … 1.23.0 ship x64. `@huggingface/transformers` 4.x pins `onnxruntime-node` ≥ 1.24.3 → on this
Intel Mac only the 3.x line runs natively (3.8.1 → 1.21.0, which also covers macOS arm64, Linux x64/arm64, Windows x64/arm64).

## Mistakes
- The newest `@huggingface/transformers` 4.3.2 was installed first — its `onnxruntime-node` 1.30.0 has no Intel Mac binary (seen in the
  package before any run, not at run time on a node). Pinning a package by «latest» on this Mac would have broken the install.
- The first batch numbers compared Node cutting at 512 tokens (the tokenizer config's `model_max_length`) with Python at 128 — Node looked
  twice as slow. The model was trained on 128 (fastembed's description: «128 input tokens truncation»): the element sets 128 itself, or
  long texts would be counted unlike the reference.
