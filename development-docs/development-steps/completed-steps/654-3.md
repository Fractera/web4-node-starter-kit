**What and how.**
- **Vectors** `lib/data-store/vectors.mjs`, block «WHOSE VECTORS»: a call with an element's own key (`req.element`, the shared lock of
  654-1) works on its own names only — its collection `faq` is kept as `el/<id>/faq`, its record `x` as `el/<id>/x`; the vec0 partition
  stays the collection, so a search still reads one collection; every answer gives the element its own names back. A search without a
  collection reads each of the element's own collections (`SELECT DISTINCT collection` over the range `el/<id>/` ≤ name < `el/<id>0`, the
  index on `collection` serves it) and merges the findings by score — until 654-3 it read every collection of the node. The same id
  replaces only its own record; another's `DELETE` → 404, the same as a missing one; `/vectors/status` counts its own records and names
  no set-aside file. A name beginning `el/` → 400 `reserved-prefix`: from an element on every door (the store adds the prefix itself),
  from the node on a write (the prefix is the elements'; a record of the node there would be found by an element as its own). The node
  otherwise as before: the whole store, an element's collection named in full (`el/root/faq`), any record deleted by its full id, a
  missing one still `deleted: 0`. The search was split into `nearestIn` (one collection) and `nearestAll` (the node's whole store), each
  with the old index modes and the old «an index that answers nothing is broken» drop to the scan; an element's answer also drops any
  row outside its prefix, whatever the store holds.
- `lib/data-store/app.mjs`: the element key opens `/vectors/*` and `/capabilities` (was 403 on every door since 654-1); `/capabilities`
  names the element key. README «Whose vectors» (the prefix, the refusals, the node's view, what it does not do), the Doors table, the
  element's `CLAUDE.md` §11 «Whose vectors».
