# Task for the creator agent (Mac): an element's data road — the key and the local file (Roma, Telegram 332, 2026-11-24 15:37 UTC)

From the main agent of the server node fractera.ai (core build bf75a3ef). Two systemic defects found by the Fractera marketplace element
(lidt5: born from the native template v0.1.81, registered custom, walled) and checked against the templates' code on GitHub. No keys or
personal data in this file.

## 1. A native-template element registered custom cannot reach the data layer (systemic; lidt5, 2026-11-24 15:16 UTC+1)

- Fact (the element's own report): lidt5's `DATA_SECRET` is empty, `REMOTE_DATA_URL` is set, the data layer answers it 401, and `lib/db`
  silently falls back to a local `data/app.db`.
- Cause, read in the templates on GitHub: native v0.1.81 `lib/fractera/data-service.ts` line 20 takes only `DATA_API_KEY || DATA_SECRET`
  and sends `X-Data-Secret`. Custom v0.3.238 takes `X-Element-Key` from `ELEMENT_KEY` (line 26). The core's installer (818-7c,
  `lib/web4-items/element-env-keys.mjs`) withholds `DATA_SECRET` from every registry kind `user`. lidt5 was born from the native template
  into kind `user`, so its code asks for the one key it is never given. The wall is right; the birth combination is not checked.
- Needed: either `create` refuses a native template into kind `user` (or rewrites data-service at birth), or the native template's
  data-service falls back to `ELEMENT_KEY` / `X-Element-Key` when `DATA_SECRET` is empty. A silent fallback to local SQLite on a node
  should be a loud error (`[db] remote key missing`), not a quiet file.
- Proof of the fix: an element born native into kind `user` writes a row and reads it back through the data layer (200), with no
  `data/app.db` created; a true native element still uses `X-Data-Secret`.

## 2. The local database road writes into the build folder (systemic, every template; lidt5, 2026-11-24 16:35 UTC+1)

- The element's words: the local road of `lib/db` opens `process.cwd()/data/app.db`, but a live element runs from `.next-a/standalone`
  or `.next-b/standalone`, so a local-road database sits inside a build folder the next deploy replaces — lost at the second deploy.
- Confirmed in the code: `lib/db/index.ts` — custom v0.3.238 line 600, native v0.1.81 line 601:
  `process.env.APP_DB_PATH ?? join(process.cwd(), "data", "app.db")`. The standalone cwd is the element's report, not checked by me.
- Needed: the default `APP_DB_PATH` under `SERVICE_DATA_DIR` (outside the build), and on a node the local road only with a loud warning
  (it is reached only when the remote key is missing — section 1).
- Proof: write a row on the local road, deploy twice (a → b → a), the row is still there.
